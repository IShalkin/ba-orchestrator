## Группа 1. Методы исследования ситуации

### 1.1 Интервью (Interviews)
- Проблема: Неясность требований и скрытые проблемы
  - Какой тип неопределенности: Непонимание реальных нужд стейкхолдеров
- Этапы: Discovery, elicitation, analysis
- Входные данные: Интервью, бизнес-проблема, документация
- Результат: Протоколы встреч, требования, информация обситуации
- Участники: BA, Sponsor, SME, End User
- Процедура: 1. Подготовка вопросов. 2. Согласование встречи. 3. Проведение интервью. 4. Фиксация результатов. 5. Согласование протокола.
- Вопросы аналитика: 'Почему это необходимо?', 'Какая главная проблема возникает?', 'Кто принимает решения?'
- Артефакты: Интервью-гайд, протокол встречи, аудиозапись
- Пример: Интервью с менеджером склада для выявления задержек упаковки
- Проверка качества: Review с участником интервью, подтверждение фактов
- Ошибки: Субъективность ответов, отсутствие четкой цели
- Когда не использовать: Маленький риск, известный домен, срочная гипотеза без доступа к людям
- Альтернативы: Анкетирование, наблюдение, фокус-группы
- Связь с решениями: Scope, priority, acceptance
- Адаптация для AI: Автоматическая транскрипция, суммаризация, human-in-the-loop для проверки галлюцинаций

### 1.2 Семинары и воркшопы (Workshops)
- Проблема: Разрозненность мнений стейкхолдеров
  - Какой тип неопределенности: Конфликты требований и несогласованность целей
- Этапы: Elicitation, collaboration, analysis
- Входные данные: Бизнес-цели, проблемы, предметная область
- Результат: Согласованные требования, модели, список задач
- Участники: BA (фасилитатор), Sponsor, SME, End User
- Процедура: 1. Определение повестки. 2. Приглашение участников. 3. Проведение сессии с упражнениями. 4. Фиксация идей. 5. Рассылка итогов.
- Вопросы аналитика: 'Какие общие цели преследуем?', 'Какие препятствия на пути к цели?'
- Артефакты: Повестка, флипчарты, протокол воркшопа, модели
- Пример: Совместное построение процесса 'as-is' с ключевыми сотрудниками
- Проверка качества: Подтверждение участниками итогового документа
- Ошибки: Доминирование одного участника, отсутствие четкой повестки
- Когда не использовать: Малый масштаб задач, отсутствие ключевых фигур
- Альтернативы: Индивидуальные интервью, опросы
- Связь с решениями: Scope, priority, architecture
- Адаптация для AI: Инструменты совместного виртуального мозгового штурма с ИИ-ассистентом

### 1.3 Анализ документов (Document Analysis)
- Проблема: Отсутствие понимания существующих регламентов и систем
  - Какой тип неопределенности: Нехватка фоновых знаний о текущем состоянии
- Этапы: Discovery, elicitation, analysis
- Входные данные: Существующая документация, регламенты, контракты, стандарты
- Результат: Список правил, извлеченные требования, глоссарий
- Участники: BA, Compliance/Legal, SME
- Процедура: 1. Сбор документов. 2. Чтение и выделение ключевых фрагментов. 3. Синтез информации. 4. Верификация с экспертом.
- Вопросы аналитика: 'Какие действующие правила описаны?', 'Какие ограничения наложены регулятором?'
- Артефакты: Выписки, сводные таблицы, глоссарий
- Пример: Анализ договора поставки для выявления системных ограничений
- Проверка качества: Экспертная проверка полноты извлеченных данных
- Ошибки: Устаревшая документация, не отражающая реальность
- Когда не использовать: Документация полностью отсутствует или неактуальна
- Альтернативы: Интервью, наблюдение
- Связь с решениями: Compliance, scope
- Адаптация для AI: Использование RAG-систем для автоматического извлечения сущностей из текстов

### 1.4 Наблюдение (Observation)
- Проблема: Расхождение между документированными и реальными процессами
  - Какой тип неопределенности: Неявное знание (tacit knowledge), искажение фактов в словах
- Этапы: Discovery, elicitation
- Входные данные: Рабочее место, операционные процессы, сотрудники
- Результат: Описание реального процесса ('as-is'), фиксация проблем
- Участники: BA, End User, Operational Support
- Процедура: 1. Согласование визита. 2. Пассивное или активное наблюдение за работой. 3. Фиксация шагов. 4. Уточняющие вопросы.
- Вопросы аналитик: 'Почему этот шаг выполняется именно так?', 'Какие трудности возникают при сбое?'
- Артефакты: Заметки наблюдателя, хронометраж, схемы шагов
- Пример: Наблюдение за оператором колл-центра при обработке инцидента
- Проверка качества: Сравнение заметок с реальностью, ревизия с сотрудником
- Ошибки: Эффект Хоторна (изменение поведения людей из-за наблюдения)
- Когда не использовать: Удаленная работа без инструментов трансляции, жесткие ограничения безопасности
- Альтернативы: Интервью, анализ специальных записей
- Связь с решениями: Scope, acceptance
- Адаптация для AI: Анализ записей экранов с помощью комп. зрения (Process Mining)

### 1.5 Анализ корневых причин (Root Cause Analysis)
- Проблема: Лечение симптомов вместо устранения истинной причины
  - Какой тип неопределенности: Непонимание глубинной природы проблемы
- Этапы: Analysis, discovery
- Входные данные: Инциденты, проблемы, жалобы стейкхолдеров
- Результат: Диаграмма причинно-следственных связей, корневая причина
- Участники: BA, SME, Operational Support
- Процедура: 1. Формулировка проблемы. 2. Задавание вопроса 'Почему?' 5 раз (Fishbone / 5 Whys). 3. Определение корневой причины. 4. Разработка мер.
- Вопросы аналитика: 'Почему это произошло?', 'Что вызвало данное отклонение?'
- Артефакты: Диаграмма Исикавы (Fishbone), дерево причин
- Пример: Анализ частых возвратов товара: брак поставщика -> слабый входной контроль
- Проверка качества: Подтверждение причинно-следственной логики экспертами
- Ошибки: Остановка на промежуточных симптомах, субъективизм
- Когда не использовать: Проблема очевидна и требует немедленного исправления
- Альтернативы: Анализ бизнес-событий, мозговой штурм
- Связь с решениями: Scope, architecture, priority
- Адаптация для AI: Автоматический анализ логов ошибок для поиска первопричин с помощью LLM

### 1.6 Анализ пробелов (Gap Analysis)
- Проблема: Непонимание разницы между текущим и целевым состоянием
  - Какой тип неопределенности: Отсутствие моста между 'as-is' и 'to-be'
- Этапы: Analysis, strategy analysis
- Входные данные: Current state description, Future state description
- Результат: Список пробелов (gaps), план преодоления разрывов
- Участники: BA, Architect, Sponsor, SME
- Процедура: 1. Описание текущего состояния. 2. Описание целевого состояния. 3. Сопоставление моделей. 4. Выявление отсутствующих элементов.
- Вопросы аналитика: 'Чего не хватает в текущей системе для достижения цели?'
- Артефакты: Таблица разрывов (Gap matrix), перечень требований к переходу
- Пример: Сравнение текущих навыков сотрудников с требованиями нового ПО
- Проверка качества: Валидация разрывов с архитекторами и бизнесом
- Ошибки: Поверхностное сравнение без учета скрытых зависимостей
- Когда не использовать: Создание продукта с нуля (нет текущего состояния)
- Альтернативы: SWOT-анализ, бизнес-архитектура
- Связь с решениями: Scope, architecture, release
- Адаптация для AI: Автоматическое сопоставление спецификаций и кодовой базы через ИИ

## Группа 2. Методы моделирования и спецификации

### 2.1 Моделирование бизнес-процессов (Business Process Modelling / BPMN)
- Проблема: Непонимание последовательности работ и зон ответственности
  - Какой тип неопределенности: Хаос в операционной деятельности, петли и узкие места
- Этапы: Analysis, specification, design definition
- Входные данные: Интервью, регламенты, наблюдения, бизнес-цели
- Результат: Модель процессов 'as-is' и 'to-be' со схемой swimlanes
- Участники: BA, Process Owner, End User, Developer
- Процедура: 1. Определение границ процесса и триггеров. 2. Фиксация шагов и решений. 3. Добавление ролей (swimlanes). 4. Анализ узких мест.
- Вопросы аналитика: 'Что запускает процесс?', 'Кто принимает решение на этом развилке?'
- Артефакты: Диаграмма BPMN, матрица ролей
- Пример: Моделирование процесса обработки заказа клиента от создания до отгрузки
- Проверка качества: Прохождение сквозного сценария с владельцем процесса
- Ошибки: Чрезмерная детализация или упущение исключений
- Когда не использовать: Статические непроцессные задачи, творческие исследования
- Альтернативы: Текстовые сценарии, функциональная декомпозиция
- Связь с решениями: Scope, architecture, acceptance
- Адаптация для AI: Генерация BPMN схем по текстовым описаниям с помощью LLM

### 2.2 Варианты использования (Use Cases)
- Проблема: Неточное описание функциональных требований к системе
  - Какой тип неопределенности: Непонимание взаимодействия пользователя и системы
- Этапы: Specification, requirements analysis
- Входные данные: Стейкхолдерские требования, бизнес-процессы
- Результат: Диаграмма вариантов использования и подробные спецификации (Use Case Descriptions)
- Участники: BA, Developer, Tester, End User
- Процедура: 1. Выявление актеров. 2. Определение целей актеров (Use Cases). 3. Описание основного потока событий. 4. Описание альтернативных и исключительных потоков.
- Вопросы аналитика: 'Какую задачу решает актер?', 'Что происходит, если система недоступна?'
- Артефакты: Use Case Diagram, Use Case Specification
- Пример: Use Case 'Оплата заказа банковской картой'
- Проверка качества: Review с разработчиками и тестировщиками (покрытие всех веток сценария)
- Ошибки: Избыток деталей пользовательского интерфейса в бизнес-логике
- Когда не использовать: Проекты без программной логики, чисто организационные изменения
- Альтернативы: User Stories, функциональная декомпозиция
- Связь с решениями: Scope, architecture, acceptance
- Адаптация для AI: Автоматическая генерация тест-кейсов из описаний Use Case

### 2.3 Пользовательские истории (User Stories)
- Проблема: Бюрократичность тяжелых спецификаций в Agile
  - Какой тип неопределенности: Разрыв между потребностью бизнеса и пониманием разработчиков
- Этапы: Specification, backlog management, elicitation
- Входные данные: Цели пользователей, бэклог продукта, концепция
- Результат: Карточки User Stories с критериями приемки (Acceptance Criteria)
- Участники: Product Owner, BA, Developer, Tester, End User
- Процедура: 1. Формулировка по шаблону (Как... Хочу... Чтобы...). 2. Определение критериев приемки (INVEST). 3. Приоритезация в бэклоге.
- Вопросы аналитика: 'Какую ценность это приносит пользователю?', 'Как мы проверим, что задача выполнена?'
- Артефакты: Бэклог продукта, карточки истории, acceptance criteria
- Пример: 'Как зарегистрированный пользователь, я хочу восстановить пароль по email, чтобы зайти в аккаунт'
- Проверка качества: Соответствие критериям INVEST, согласование с PO
- Ошибки: Слишком крупный размер историй (эпики вместо историй), отсутствие критериев приемки
- Когда не использовать: Жесткие регулируемые системы с неизменяемым контрактом (Waterfall)
- Альтернативы: Use Cases, SRS-документы
- Связь с решениями: Scope, priority, release, acceptance
- Адаптация для AI: ИИ-помощник для декомпозиции эпиков на User Stories и генерации критериев приемки

### 2.4 Анализ бизнес-правил (Business Rules Analysis)
- Проблема: Неструктурированная политика и логика принятия решений
  - Какой тип неопределенности: Неявные ограничения, разбросанные по документам
- Этапы: Analysis, specification
- Входные данные: Регламенты, законы, интервью со специалистами
- Результат: Каталог бизнес-правил, таблицы решений, деревья решений
- Участники: BA, Legal/Compliance, Domain SME, Developer
- Процедура: 1. Выявление ограничений и условий. 2. Классификация правил (термины, факты, действия). 3. Оформление в виде таблиц или выражений.
- Вопросы аналитика: 'При каких условиях применяется эта скидка?', 'Какой закон или норма регулирует это правило?'
- Артефакты: Таблицы решений (Decision tables), каталог правил
- Пример: Таблица расчета кредитного рейтинга в зависимости от стажа и дохода
- Проверка качества: Проверка на непротиворечивость и полноту комбинаций в таблице
- Ошибки: Смешение бизнес-правил с техническими ограничениями реализации
- Когда не использовать: Отсутствие сложной логики и вариативности принятия решений
- Альтернативы: Текстовые требования, блок-схемы
- Связь с решениями: Compliance, architecture, acceptance
- Адаптация для AI: Автоматическое извлечение таблиц решений из текста нормативных актов

## Группа 3. Стратегический анализ и оценка ценности

### 3.1 SWOT-анализ
- Проблема: Отсутствие целостного видения позиции организации
  - Какой тип неопределенности: Непонимание внешних угроз и внутренних слабых мест
- Этапы: Strategy analysis
- Входные данные: Рыночные данные, стратегия компании, результаты интервью
- Результат: Матрица SWOT (Strengths, Weaknesses, Opportunities, Threats)
- Участники: Sponsor, BA, Business Owner, Management
- Процедура: 1. Определение сильных и слабых сторон (внутренние факторы). 2. Определение возможностей и угроз (внешние факторы). 3. Сопоставление и выработка стратегии.
- Вопросы аналитика: 'В чем наше ключевое преимущество перед конкурентами?', 'Какие рыночные тренды несут угрозу?'
- Артефакты: SWOT-матрица, стратегические инициативы
- Пример: Анализ выхода онлайн-ритейлера на рынок доставки продуктов
- Проверка качества: Экспертная оценка реалистичности факторов топ-менеджментом
- Ошибки: Слишком общие формулировки, субъективизм без опоры на факты
- Когда не использовать: Локальные технические задачи внутри существующего продукта
- Альтернативы: PESTLE, Balanced Scorecard, Business Model Canvas
- Связь с решениями: Scope, priority, business case
- Адаптация для AI: Автоматический сбор рыночной аналитики и новостей для формирования угроз и возможностей

### 3.2 Бизнес-кейсы (Business Cases)
- Проблема: Отсутствие обоснования целесообразности инвестиций
  - Какой тип неопределенности: Неопределенность окупаемости и финансовой ценности
- Этапы: Strategy analysis, solution evaluation
- Входные данные: Оценки стоимости, прогнозируемые выгоды, риски
- Результат: Документ бизнес-кейса с расчетом ROI, NPV и срока окупаемости
- Участники: Sponsor, BA, Financial Analyst, Business Owner
- Процедура: 1. Описание бизнес-потребности. 2. Оценка затрат (TCO). 3. Оценка выгод. 4. Финансовый анализ (NPV, ROI). 5. Защита перед спонсором.
- Вопросы аналитика: 'Каков финансовый возврат на вложенный капитал?', 'Какие риски могут сорвать окупаемость?'
- Артефакты: Документ бизнес-кейса, финансовая модель
- Пример: Расчет окупаемости внедрения автоматизированного склада за 2 года
- Проверка качества: Финансовый аудит, согласование с финансовым директором
- Ошибки: Завышение выгод и занижение затрат на разработку и поддержку
- Когда не использовать: Обязательные регуляторные требования (compliance), где выбор не стоит
- Альтернативы: Анализ затрат и выгод (Cost-Benefit Analysis)
- Связь с решениями: Scope, priority, release, business case
- Адаптация для AI: Использование предиктивных моделей для симуляции финансовых сценариев

### 3.3 Бизнес-модель Canvas (Business Model Canvas)
- Проблема: Отсутствие целостного понимания того, как бизнес создает ценность
  - Какой тип неопределенности: Разрозненность элементов бизнес-логики нового продукта
- Этапы: Strategy analysis, definition
- Входные данные: Цели предприятия, рыночные гипотезы, потребности клиентов
- Результат: Заполненная канва из 9 блоков бизнес-модели
- Участники: Sponsor, BA, Product Manager, SME
- Процедура: 1. Определение сегментов клиентов и ценностных предложений. 2. Описание каналов и отношений. 3. Оценка ключевых ресурсов, партнеров и процессов. 4. Расчет доходов и затрат.
- Вопросы аналитика: 'Кто наши ключевые клиенты?', 'Какую ценность мы им доставляем?'
- Артефакты: Схема Business Model Canvas
- Пример: Описание бизнес-модели сервиса подписки на кофейные зерна
- Проверка качества: Внутренняя непротиворечивость блоков доходов и затрат
- Ошибки: Слишком поверхностное заполнение блоков без подтверждения гипотез
- Когда не использовать: Внутренние технические рефакторинги систем
- Альтернативы: Value Proposition Canvas, SWOT
- Связь с решениями: Scope, business case, architecture
- Адаптация для AI: Интерактивное тестирование жизнеспособности блоков с помощью генеративного ИИ
