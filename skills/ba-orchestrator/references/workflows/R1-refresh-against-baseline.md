# WF-R1 — Refresh Against a Baseline (changed sources → drift report for change control)

**Use when:** a baseline run already exists (its requirement catalogues, `trace.csv` files and `coverage-summary.json` are `done`), and its sources have changed since: for example a weekly re-check of the issue tracker against the agreed requirements.
**Not when:** there is no baseline run (use WF-E2 or WF-E4 first), or the scope or goals changed (that is a new run, not a refresh).
**Composes:** T6.4 (traceability) + T7 (quality audit) + T6.5 (change control).
**Brief must contain:** the baseline run directory, which sources changed and since when, and who owns change control.
**Deliverables:** a refreshed merged trace, a new `coverage-summary.json`, and a drift report against the baseline.

## Rules
- **The baseline is read-only input.** Executors trace against the baseline run's requirement catalogues; they do not add, split or reword requirements. A candidate new requirement is listed in the drift report and goes to change control. It enters the catalogue only when change control approves it, in a separate run.
- **Re-stage only what changed**, issue-tracker export first (`source-access.md` §4), into a new staging directory. Unchanged staged sources are reused by path from the baseline run.
- New run directory, `RS init … --baseline <baseline run dir>`: the baseline's tree hash is recorded, `RS reconcile` reports any change to it and `completed` is refused. The brief names the baseline run. Register every executor with `--depends-on` its upstream keys (run-protocol §4).

## Waves
| Wave | Executors (parallel inside a wave) | Depends on |
|---|---|---|
| 0 | researchers on the changed sources only | staging |
| 1 | `requirements-traceability`, one per capability scope of the baseline, against the baseline catalogues, each writing `trace.csv` with the fixed columns (run-protocol §8) · `requirements-quality-verification-and-analysis` on the changed or new issues | research |
| 2 | orchestrator, by script: `merge_trace.py OUT --trace <new trace.csv files> --issues <current issues.json> --baseline <baseline>/…/coverage-summary.json` writes the new `coverage-summary.json`. Its `drift` section diffs requirement coverage only (coverage changed from → to, requirement ids added, removed); it does not diff capability, scope, issue status or conflicts | 1 |
| 3 | `change-impact-analysis` for each `drift` item, and for each re-scoped or re-labelled issue the wave 1 quality executor reported (scope drift is not in the script diff, so it arrives only that way) | 2 |
| 4 | synthesizer with both coverage summaries as `MEASURED COUNTS`: the drift report | 3 |

## Drift report (in the synthesis)
Measured by script, counts used as given:
- Requirements whose coverage changed (from → to), added or removed: the wave 2 `drift` section, with the issues that caused each change.
- Current issues that reference no baseline requirement: `unreferenced_issues` in the new summary.
- Current conflict rows: `conflict_rows` in the new summary.

Reported by executors, with evidence, and labelled as not script-measured (no script diffs these against the baseline):
- Issues cancelled, closed, re-labelled or re-scoped since the baseline.
- Conflicts opened and conflicts closed, by comparing the current `conflict_rows` with the baseline's.
- Candidate new requirements, each marked for change control.

## Gates
- Plan gate: confirm the baseline run and the changed sources.
- At the end: hand the drift report to the change-control owner. The output feeds WF-T6 wave 3 (`change-control`, `change-impact-analysis`); this workflow does not update the baseline (`requirements-baselines-and-version-control`).

## Light mode (incremental, script-first)
**Use when:** the baseline run has a baseline page (SKILL.md step 4c) and the question is what changed in the tracker, the deck or the whiteboard since, for example weekly. The requirements are not re-derived: new and changed tracker items are mapped onto the baseline catalogues one by one, and requirements whose cited source changed are listed for a person to review. Use the full waves above when the traceability itself must be redone.

**State** lives in one directory outside both runs (for example `ba-runs/<baseline run>-refresh/`), written only by the scripts and the orchestrator. Never delete it: it is the only record of what the page was built on.

| File | Written by | What |
|---|---|---|
| `baseline.json` | `init_state.py`, `accept.py` | Slide text per deck, widget signatures per whiteboard, by source name |
| `tracker/now.json`, `tracker/export-text.json` | `init_state.py`, `tracker_merge.py` | Current state per item key (status, text hash, in the baseline export or not); the export's letters+digits text |
| `tracker/pulls/<date>.json` | orchestrator, by script | Raw pulls in the pull format, kept |
| `tomap.json`, `mappings.csv` | `tracker_merge.py`, `apply_mappings.py` | Items still to map (cumulative); item → requirement ids with effect and the justifying quote |
| `flags.json`, `review.json` | `tracker_merge.py`, `source_check.py`; `build_baseline.py` | What changed; the requirements to review because of it (never on the page) |
| `curated.json` | orchestrator, after review | `coverage_overrides` (with a reason each) and extra `conflicts` |
| `state.json` | the scripts | `tracker_last_updated` watermark, input md5s, every acceptance |

Scripts are in `scripts/refresh/`; `--help` prints each one's full usage.

1. **Once:** `init_state.py STATE --tracker-export <issues.json the trace was built on> --ac-field <field> --deck <id>=<deck> --whiteboard <id>=<widgets.json> --cancelled-status <the set merge_trace.py --exclude-status used>`. Pass the same files the baseline researchers read; the whiteboard field paths (`--map`) are fixed here and every later check and accept uses them. Then build the page once (step 5): it writes `requirement-ids.json` and `traced-keys.json`, which the first merge and the first mapping read. Each `<id>` (letters, digits, `_`, `-`) is the stable source id: copy the manifest to `STATE/manifest.json`, give each deck and whiteboard source the same `"id"`, and add `"refresh_state": "<STATE>"`. Flags bind to sources by that id only; `build_baseline.py` refuses a flag whose id is no manifest source of that kind. The cancelled-status set is recorded once in `state.json` and used by the merge and the page, and must equal the baseline summary's excluded statuses.
2. **Tracker:** pull the items updated since `tracker_last_updated` (minus a margin) with the full field list: description, the acceptance-criteria field (named, never "all fields") and `updated`, **ordered `updated ASC` and paged to the end**. Write the raw response by script, never retyped, to `STATE/tracker/pulls/<date>.json` as `{"query": "<the query>", "total": <the tracker's own count of matches>, "items": [{key, summary, status, labels, issuetype, parent_key, assignee, created, updated, description, ac}, …]}`, then run `tracker_merge.py STATE <pull>`. A pull with total 0 is recorded as a pull. It refuses a pull whose items do not number exactly its total (one page of a newest-first result would move the watermark past every item it dropped, for good), a pull that lacks description, ac or updated (a compact view drops them silently), and an empty summary, description or ac on an item that had text there before (`--allow-empty-summary` / `--allow-empty-description` / `--allow-empty-ac KEY` when it was really deleted). A change of an item's coverage category is flagged in either direction: cancelled (`cancelled_keys`) and live again after cancelled (`reopened_keys`); done or not done is no coverage category (a requirement is covered when it is written, not when it is built). A baseline-export item live again after being cancelled is new work: it goes to `tomap.json` and onto the page's list of items no requirement references like a new item. One the baseline trace already places is reviewed (listed under its requirement as re-opened), not mapped: it never enters `tomap.json`, because every build writes the trace's keys to `STATE/traced-keys.json` and `tracker_merge.py` skips them. An item's text is its summary, description and ac, compared as letters and digits of any script, case-folded, with the symbols that change a number's meaning kept as tokens (a comparator or `=` before a number, a sign before a digit, a decimal point or comma between digits, `%` after and `±` before a number: `< 2 s` → `> 2 s`, `1.5` → `15`, `-20` → `20`, `2-5 days` → `25 days` are changes); a wiki strikethrough `-…-`, a markdown blockquote `>` at a line start, a setext heading rule (`===` / `---` alone on a line) and emphasis between a symbol and its number (`< *2 s*`) are not content; at the first live sighting, ordered-list markers and embedded image names are not content either. A text field the tracker returns as a list or an object is read as text. The first live sighting of a baseline-export item is flagged when any number or negation word (`not`, `no`, `never`, `neither`, every `n't` contraction, …) differs from the export, or its text similarity falls below 0.9.
3. **Map** when it prints `to map N` with N > 0. One subagent maps each item in `tomap.json` onto requirement ids, writing `key,text_hash,req_ids,effect,quote,note` (`text_hash` copied from `tomap.json`). Map only when the item's text states the requirement's behaviour (a shared topic is not enough); `quote` is that sentence; `effect` is exactly one of `adds to existing coverage`, `upgrades none->partial`, `upgrades partial->full`, `no requirement`, `new requirement candidate`, `conflicts with <ids>`, `descopes <ids>` (a trailing `(note)` is allowed). `req_ids` may use any separator; one row per key. Run `apply_mappings.py STATE <mapped.csv>`: a row may also amend the mapping of an item already mapped at its current text. It refuses, writing nothing, a key neither in `tomap.json` nor such an amendment, a key given twice, a requirement id in no catalogue (`STATE/requirement-ids.json`, written by every build: build once before the first mapping), a `text_hash` that is not tomap's, an effect outside the list, a `conflicts with` / `descopes` effect whose named ids are not in `req_ids`, and a quote that is missing, shorter than 4 words and 20 letters (digits do not count), or not a run of whole words of the item's text; it replaces `mappings.csv` atomically, and exits 1 naming every item still unmapped. Spot-check every `upgrades` and `conflicts` row against the item text.
4. **Deck and whiteboard:** download the current files (check size and type, `source-access.md` §4) and run `source_check.py STATE deck <file> --id <id>` and `source_check.py STATE whiteboard <file> --id <id>`. Slides are matched by text, one occurrence to one occurrence (a slide text that appears twice is matched twice), so a moved slide is reported as moved, not changed, and a one-word edit is flagged; an edited slide is paired with its baseline slide by content first, and a slide rewritten past recognition is paired with the gone slide at the same position only when the neighbours on both sides did not move, so the cited numbers survive an insert, an edit or an in-place rewrite. Where an insert or a delete sits next to a heavy rewrite, nothing is guessed: the gone slide is reported changed and the new slide is listed as text no citation covers. A whiteboard check records every area each changed, added or deleted item sits in, nearest first (areas nest; a parent cycle ends the walk), and for a moved item the areas it left. Slide-number and date fields are not content, so a re-save or a renumbering is not an edit. The deck check reads the text layer only: when the md5 changed, render the changed slides and look at them.
5. **Build:** `build_baseline.py <baseline run> --manifest STATE/manifest.json --out STATE/baseline.html`. The baseline counts are still checked against the baseline summary before the overlay. A mapping counts only at the item's current text hash and while the item is live, and only `adds` and `upgrades` raise coverage: a requirement with coverage none or not traced that gains one becomes partial, never full. A stale, cancelled, `conflicts with` or `descopes` mapping raises nothing and is listed for review instead. A cancelled key of the baseline trace lifts nothing either: a requirement whose trace keys are all cancelled shows none, one with some cancelled shows full at most as partial. It prints `NEEDS REVIEW: N` and writes `STATE/review.json`: the requirements whose cited slide (any spelling: `slides 3–5`, `slide #4`, `p. 4`; a deck citation with no number is listed whenever its deck changed), whiteboard item (a whiteboard citation that names no item id is listed whenever its board changed) or tracker item changed (a citation of a whiteboard area covers the items in it at any depth), re-worded or re-opened items that no requirement references, every slide whose text is new and that is not the edit of a cited slide (an inserted slide, an edit of an uncited slide, an edit of a slide added after the baseline), new whiteboard items, changed whiteboard items no citation names, every mapping with an effect other than a plain `no requirement` at the item's current text that the review has not acknowledged (a `new requirement candidate` with no requirement id included, and a `no requirement` item re-worded since it was mapped, and a mapping naming a requirement id no catalogue holds), every item in `tomap.json` not mapped at its current text (`tracker_unmapped`: only a mapping clears it, never an accept), every deck or whiteboard source with no check in `flags.json`, a tracker never pulled into the state (`tracker_merge.py` records each pull in `state.json` → `last_pull`), and every source of a kind no script checks (wiki, file, any kind added later) until a person re-read it and ran `accept.py STATE source --id ID`, and again after every later tracker pull (a re-read belongs to one refresh cycle) — each source case a WARN too, because an unchecked source reads exactly like an unchanged one; a citation of a whiteboard area covers items moved out of it as well as items in it; all counted in N, and `reviewed`: the exact source state this review covers. It prints when each deck and whiteboard was last checked and when the tracker was last pulled: re-check whenever a newer file exists.
6. **Review** each flagged requirement against the old and new text in `flags.json` (`old_text`, `new_text`, `changed_text`). A coverage change goes into `curated.json` → `coverage_overrides` with its reason; a real conflict into `curated.json` → `conflicts` (`CF-` id, severity, topic, both sides, decider marked `[ASSUMPTION]` unless a source names one). A change that rewords a requirement, and a new whiteboard item or slide that states a need, go to the user as candidates for change control: requirement text is never edited here.
7. **Accept** only after the review: `accept.py STATE tracker`, `accept.py STATE deck <file> --id …`, `accept.py STATE whiteboard <file> --id …`, and `accept.py STATE source --id …` for a wiki or file source a person re-read (only an id this review listed, and only while no tracker pull came after the review; anything else is refused). Accepting moves the baseline and silences the flag; an accepted deck or whiteboard stays in `flags.json` as a clean check of the accepted file. One model for every source: only the state recorded in `review.json` → `reviewed` is accepted. A deck or whiteboard file must have the reviewed md5 and still be the last check (a check run after the page was built needs a rebuild and a review first); a deck keeps the cited slide numbers through the accept. `accept tracker` clears a key only while its status and text hash are those the review saw, so a cancellation from a later pull, or a key re-worded after the page was built, stays flagged; the mapping problems the review listed are acknowledged at that state, and come back when the item or its mapping changes.
8. Re-build, render the page and look at it, then report the counts: items pulled and mapped, coverage changes, new conflicts, requirements flagged.

**Ceilings, by design:** the first live sighting of a baseline-export item compares numbers and negation words exactly and the rest by a 0.9 similarity floor (export and live markup differ, so an exact comparison flags everything), so a one-word swap with neither (`CSV` to `PDF`) can pass unseen; a whiteboard widget that only moved is flagged; a slide inserted after the baseline has no cited number (its later edits are listed as new text no citation covers, not under a requirement); a slide rewritten past recognition next to an insert or a delete loses its cited number the same way (the change is listed when it happens, under the requirement, and later edits as uncited new text); an unrelated slide put in place of a deleted slide between two unmoved neighbours inherits its number (over-flags); the watermark is a string maximum, so query with a margin; the deck check cannot see a change that exists only in the render; an item deleted from the tracker never appears in an "updated since" pull, so a requirement traced to it keeps its coverage (compare a full key list when that matters); a deleted slide or whiteboard item that no citation names is listed nowhere; a manifest deck or whiteboard the state never tracked stays `never checked` (N ≥ 1) until it is added to the state or removed from the manifest; a wiki or file source is never checked by a script, only re-read by hand; the hash strip that keeps commit links from reading as account ids also hides an id glued to 20 or more hex characters (its own digits complete the 32); a plain slash path with `users` below its root in lower case is not read as a home path, and a REST path with a `home` or `Users` segment, or a root `/users/` (`GET /users/me`), refuses the page — the refusal names the requirement, evidence row, tracker item or conflict that carries it, never the matched text; a home-path segment is `Users`, `home` or `homes` anywhere in the path, or the share of a `\\server\share` / `//server/share` path whose name holds `users` or `home` (`users$`, `homedirs$`); a folder below the share named like one (`UsersApi`, `Homecare`) is not a home folder, so a profile share (`profiles$`), a home drive letter, `C:\Documents and Settings\…` split by its spaces and a remote IDE URL (`vscode.dev/tunnel/…`) are not seen, while a `localhost` URL's path is read as local; `~name` counts only before a separator (`~weekly` is prose); the symbol tokens do not cover a time (`10:00` → `1000`), a thousands separator written with a space, a power (`10^6` → `106`), a slash between digits (`1/2 day` → `12 day`) or a tilde before a number (`~5 s` → `5 s`), and a comparator that starts a line (`> 20 users`) reads as a blockquote marker; the pull check rests on the pull's own `total`: a tracker API that reports no total needs its pages counted to the end by the script that writes the pull (with `updated ASC`, a pull cut short only delays its later items to the next pull).
