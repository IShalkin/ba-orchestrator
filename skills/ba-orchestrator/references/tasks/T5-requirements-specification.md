# T5. Requirements Specification

Selection guide: each line shows what the method solves and when NOT to use it (first variant; open the card for every variant's full text).

## 5.1 User Stories and Story Mapping

- [User Stories](../methods/user-stories.md) — Captures system requirements as short, simple user-focused sentences supported by conversations and confirmation criteria, reducing bloated, unreadable specification documents. *Not for:* For complex legal contracts or heavy outsourcing agreements where formal legally binding written specifications are required upfront.
- [User Story Mapping](../methods/user-story-mapping.md) — Replaces flat, disorganized product backlogs with a structured, visual map that conveys product scope, user flow, and incremental release priorities. *Not for:* Single, isolated bug-fix tasks or small standalone script developments.
- [The 3 Cs (Card, Conversation, Confirmation)](../methods/the-3-cs-card-conversation-confirmation.md) — Eliminates rigid, misinterpreted requirement documents by replacing them with collaborative discussions and explicit verification criteria. *Not for:* Contractual fixed-price handoffs where direct conversation between builders and requestors is legally prohibited or impossible.
- [Story Workshop (Three Amigos)](../methods/story-workshop-three-amigos.md) — Prevents late-stage delivery blockers, scope creep, and inaccurate estimates caused by developers building software without deep, shared understanding of behavior details and edge cases. *Not for:* High-level strategic roadmap planning;

## 5.2 Use Cases and Scenarios

- [Use Cases](../methods/use-cases.md) — Models IT system functional scope via Use Case Diagrams and details actor-system interactions via structured Use Case Descriptions, providing clear developer and user specifications. *Not for:* For purely non-functional infrastructure performance specifications or static database schema design.
- [Business Use Case Modelling](../methods/business-use-case-modelling.md) — Models high-level business services provided by an organization/domain to actors, independent of technology or internal execution mechanics, clarifying strategic business scope. *Not for:* When analyzing micro-level software coding logic or database schema architecture.
- [Initial (Conceptual) Use Case Modelling](../methods/initial-conceptual-use-case-modelling.md) — Reduces ambiguity regarding system capabilities and aligns high-level functional expectations across business and technical teams. *Not for:* Systems with no functional user interaction (e.g., pure batch computation algorithms).
- [Base Use Case Description](../methods/base-use-case-description.md) — Reduces ambiguity and functional gaps by detailing ideal step-by-step user-system interactions without getting bogged down in edge cases. *Not for:* High-uncertainty early exploratory spikes or pure non-functional architectural changes.
- [Elaborated Use Case Description](../methods/elaborated-use-case-description.md) — Reduces edge-case failure, logic omission, and missed operational exception requirements. *Not for:* Simple linear processes with zero decision points or branching logic.
- [Use Case Relationships (Extend, Include, Generalization)](../methods/use-case-relationships-extend-include-generalization.md) — Reduces complexity and clutter in base use cases by factoring out optional, conditional, or complex incremental additions. *Not for:* When the added behavior is mandatory for the base goal or is a simple inline exception.
- [Instance Scenario Modelling](../methods/instance-scenario-modelling.md) — Reduces abstract ambiguity, clarifies complex business rules, and bridges requirements to acceptance/system test cases. *Not for:* When requirements are already fully crystallized and easily verified without concrete examples.
- [Scenarios and Storyboards for Specification](../methods/scenarios-and-storyboards-for-specification.md) — Converts complex, abstract business use case flows into easily understood, visual, or narrative step-by-step stories for stakeholders. *Not for:* Pure mathematical algorithms or background system jobs with no sequential step structure.
- [Scenario-Based Requirements Analysis](../methods/scenario-based-requirements-analysis.md) — Reduces abstractness and communication gaps between non-technical stakeholders and developers by illustrating concrete, step-by-step usage paths through the system. *Not for:* As a substitute for abstract behavioral specifications or formal logic constraints.

## 5.3 User Interface

- [Conceptual User Interface Design](../methods/conceptual-user-interface-design.md) — Reduces premature GUI design lock-in, unaligned user mental models, and missing screen information elements. *Not for:* Headless batch systems, back-end APIs, or systems without human user interfaces.
- [Virtual Windows](../methods/virtual-windows.md) — Bridging the communication gap between users and developers by visually representing stored domain data without committing to UI button/menu design prematurely. *Not for:* COTS acquisitions where existing screens cannot be altered.
- [Screens and Prototypes](../methods/screens-and-prototypes.md) — Eliminates ambiguity in complex user interface designs and ensures high usability prior to programming. *Not for:* COTS acquisition projects, or early elicitation phases where project scope is volatile.
- [Dialog Map](../methods/dialog-map.md) — Provides a high-level visual architecture of user interface display elements and screen navigation links without getting bogged down in visual screen layout details. *Not for:* When designing backend processing logic or non-interactive batch systems.
- [Display-Action-Response (DAR) Model](../methods/display-action-response-dar-model.md) — Bridges user interface layout design with backend interactive behavior, preventing ambiguous screen requirements for complex or outsourced UI development. *Not for:* For non-interactive batch processes or simple static display pages.
- [Keystroke-Level Model (KLM)](../methods/keystroke-level-model-klm.md) — Predicts and calculates the exact task execution time for experienced users on a computer interface without requiring user testing. *Not for:* Predicting learnability for novice users who do not follow predictable expert keystroke paths.

## 5.4 Business Rules and Decision Logic

- [Business Rules Analysis](../methods/business-rules-analysis.md) — Identifies and categorizes operational constraints, policies, and statutory laws that govern business decisions and process execution, reducing compliance failures and invalid decisions. *Not for:* In unconstrained creative brainstorming or visioning sessions where rules are deliberately set aside.
- [Decision Tables and Decision Trees](../methods/decision-tables-and-decision-trees.md) — Models complex combinations of conditions and their resulting actions in a rigorous grid or tree format, eliminating logic gaps, ambiguities, and redundant rules. *Not for:* For simple 1-condition binary choices (use a basic activity diagram decision diamond instead).
- [Decision Modelling](../methods/decision-modelling.md) — Reduces process complexity and maintainability issues by extracting repeatable operational decision logic and business rules out of process flows into standalone models. *Not for:* For one-off strategic decisions (use Decision Analysis instead) or simple processes with no conditional branching.
- [Tabular Requirement Representation](../methods/tabular-requirement-representation.md) — Eliminates redundant, monotonous, or prone-to-omission text lists generated by multi-variable permutations of functional requirements. *Not for:* When system actions across different scenarios do not follow a uniform, repetitive structural pattern.
- [Textual Process Descriptions (Mini-Specs)](../methods/textual-process-descriptions-mini-specs.md) — Provides precise algorithmic specifications for semi-complex functions, buttons, or methods where developer guessing is risky. *Not for:* Trivial CRUD functions or highly complex expert-level algorithms (e.g., 3D graphics rendering).

## 5.5 Non-Functional Requirements

- [Non-Functional Requirements Analysis](../methods/non-functional-requirements-analysis.md) — Reduces solution failure risks related to quality of service by specifying constraints and operational attributes (e.g., performance, security, availability) that functional features must meet. *Not for:* Rarely omitted, though deep technical NFR specification may be deferred in very early conceptual prototypes.
- [Quality Attribute Scenarios](../methods/quality-attribute-scenarios.md) — Converts vague quality claims (e.g., 'scalable', 'fast', 'secure') into precise, measurable, verifiable architecture-significant obligations. *Not for:* Low-risk, non-critical features where standard system baseline performance/security defaults suffice.
- [Planguage](../methods/planguage.md) — Defines quality requirements with extreme quantitative precision using a structured syntax for scales, meters, baseline values, and target benchmarks. *Not for:* Simple projects where standard informal quality targets suffice.
- [Open Metric and Open Target](../methods/open-metric-and-open-target.md) — Prevents arbitrary or unrealistically expensive quality targets by inviting suppliers to specify achievable metrics or performance targets based on their expertise. *Not for:* Hard real-time technical systems where targets are governed strictly by physical laws.
- [Quality Grid](../methods/quality-grid.md) — Systematically prioritizes quality factors (non-functional requirements) and identifies critical business quality concerns before specifying metrics. *Not for:* Small, trivial projects where quality needs are standard and self-evident.
- [Security Risk Assessment](../methods/security-risk-assessment.md) — Identifies threat vulnerabilities, estimates financial losses per incident, and calculates annual expected losses to prioritize security safeguards. *Not for:* Minor non-critical applications holding no sensitive data or financial assets.
- [Roles and Permissions Matrix](../methods/roles-and-permissions-matrix.md) — Reduces security breaches, governance failures, and activity gaps by defining role authorities, data access permissions, and segregation of duties. *Not for:* On open-access public systems where all users possess identical, unrestricted permissions.
- [Standards as Requirements](../methods/standards-as-requirements.md) — Transfers detailed regulatory, platform, or interface specifications to external standard documents, avoiding redundant specification writing. *Not for:* When custom, project-specific behavior is required that contradicts public standards.

## 5.6 Requirements Documents and Phrasing

- [PEGS Standard Plan](../methods/pegs-standard-plan.md) — Replaces outdated requirements document structures (like IEEE 830) with a modern, comprehensive 4-book structure addressing missing domain context, unstated assumptions, poor project planning, and fragmented system… *Not for:* Trivial micro-projects where formal specifications incur unnecessary overhead and full 4-book structure is excessive.
- [Requirements Specification Templates (SRS)](../methods/requirements-specification-templates-srs.md) — Provides a standardized structure to reduce ambiguity, omissions, and lack of shared understanding regarding product overview, functional capabilities, interface constraints, and quality attributes. *Not for:* Small-scale, low-risk agile iterations where lightweight user stories and acceptance tests provide adequate shared understanding with acceptable risk.
- [Requirements Engineering Process (End-to-End)](../methods/requirements-engineering-process-end-to-end.md) — Reduces ambiguity, miscommunication, scope creep, conflicting requirements, and solution delivery failure. *Not for:* When using a pure COTS package with zero customization allowed, though user needs still drive selection.
- [Requirement Writing Patterns](../methods/requirement-writing-patterns.md) — Eliminates ambiguity, misinterpretation, inconsistent granularity, unquantifiable targets, and confusion across diverse team audiences. *Not for:* When non-textual representations (visual models, prototypes, decision tables) convey the specific rule or design more clearly and efficiently.
- [EARS](../methods/ears.md) — Reduces ambiguity, subjective phrasing, compound obligations, and unstructured natural language requirements. *Not for:* High-level goal setting or open-ended exploratory product discovery.
- [Feature Requirements](../methods/feature-requirements.md) — Communicates required product functionality clearly in traditional textual format for simple extensions or technical component purchases. *Not for:* COTS business application tenders where feature lists lock out superior standard software workflows.
- [Development Process Requirements](../methods/development-process-requirements.md) — Mitigates high requirement uncertainty or scope volatility by specifying the development and change management process rather than fixed product features. *Not for:* Simple, well-known COTS purchases with fixed, non-negotiable scopes.
- [Glossary](../methods/glossary.md) — Reduces semantic ambiguity, misunderstandings, and defects caused by 'kidnapped words' (ordinary words used in a specialized domain sense), acronym confusion, or conflicting terminology among stakeholders. *Not for:* Never omit;

## 5.7 Specification by Example and Acceptance Criteria

- [Specification by Example](../methods/specification-by-example.md) — Eliminates miscommunication, functional gaps, unnecessary rework, and outdated documentation by establishing precise, testable, and collaboratively defined specifications. *Not for:* Not recommended when stakeholder access is completely absent with no proxy, on one-off throwaway prototypes, or for purely non-deterministic subjective requirements…
- [Acceptance and Fit Criteria](../methods/acceptance-and-fit-criteria.md) — Eliminates ambiguity and subjectivity in requirements, making soft, vague, or complex functional/non-functional requirements testable and verifiable. *Not for:* None;

## 5.8 Formal Specification

- [Formal Picnic](../methods/formal-picnic.md) — Eliminates subtle ambiguities, internal contradictions, falsehoods, and edge-case oversights in critical requirements by deriving precise mathematical models and converting them back into crystal-clear natural language. *Not for:* Non-critical, rapidly changing UI prototype ideas where mathematical rigor offers little ROI.
- [Abstract Data Type (ADT) Specification](../methods/abstract-data-type-adt-specification.md) — Provides a purely external, mathematical specification of data types based strictly on available operations and axioms, eliminating overspecification and providing a formal definition of completeness. *Not for:* Simple static configuration files or unstructured data blobs.
- [Real-Time Temporal Logic (LTL)](../methods/real-time-temporal-logic-ltl.md) — Reduces imprecision, ambiguous interpretations, and lack of mathematical verifyability in declarative goals, requirements, assumptions, and domain properties. *Not for:* For low-risk, non-critical requirements where structured natural language templates provide sufficient precision at lower cost.
- [Z Specification](../methods/z-specification.md) — Reduces ambiguity, structural vagueness, and unverified state transformations in complex object-oriented transactional systems. *Not for:* For reactive, real-time control systems where temporal ordering and event-driven triggers are dominant (use SCR or LTL instead).
- [SCR Event-Based Specification](../methods/scr-event-based-specification.md) — Reduces incompleteness, non-determinism, and unhandled event combinations in reactive software controllers. *Not for:* For large, highly hierarchical transactional systems requiring complex object structuring and relational calculus.
- [Algebraic Specification](../methods/algebraic-specification.md) — Reduces implementation bias and state-representation overhead by defining domain concepts abstractly through equations on operation compositions. *Not for:* When system state dynamics and temporal event sequences are the primary concern of requirements engineering.
- [Formal Specification Overview (LTL, Z, SCR)](../methods/formal-specification-overview-ltl-z-scr.md) — Eliminates ambiguity, noise, and incompleteness by providing a mathematically precise, machine-processable specification amenable to automated proof, model checking, and animation. *Not for:* In low-risk, non-critical commercial projects where informal/semi-formal documentation suffices and formal verification costs are unjustified.
