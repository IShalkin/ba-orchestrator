# Prototyping for Elicitation

`T2 Situation Investigation and Elicitation › 2.8 Prototypes and Scenarios for Elicitation`

**Also described as:** Mock-ups and Prototyping; Prototyping; Prototyping for Requirements (Sacrificial Prototyping); Requirements Prototyping

This card merges 6 descriptions of the method, labelled Variant A–F in every field.

## Problem Solved

**[Variant A]**

Reduces uncertainty when stakeholders do not know or cannot articulate what they need until they see a concrete representation.

**[Variant B]**

Reduces uncertainty, cognitive distance, and misinterpretation regarding dynamic user interface interactions and complex system functionalities.

**[Variant C]**

Reduces uncertainty around user interaction and usability requirements; prevents stakeholder mismatch by providing early, concrete visual feedback.

**[Variant D]**

Constructs working models (Throwaway or Evolutionary) of proposed software/screens to clarify requirements and test usability, reducing post-implementation rework.

**[Variant E]**

Reduces misinterpretation and unsubstantiated user assumptions by providing an early visual or functional approximation of the proposed solution for rapid feedback.

**[Variant F]**

Concretizes vague, abstract requirements, allows users to visualize proposed solutions, and uncovers missing functional/usability requirements early.

## Prerequisites

**[Variant A]**

Basic understanding of the problem boundary and candidate business event use cases.

**[Variant B]**

**[Variant C]**

Identified user roles and initial understanding of target functional features.

**[Variant D]**

Selected scope, agreed fidelity level (low/high), and clear session objectives (Business, Usability, or Capacity).

**[Variant E]**

Initial understanding of target user tasks and interface goals.

**[Variant F]**

Identified user goals and key operational scenarios to explore.

## Step-by-Step Procedure

**[Variant A]**

Select a business use case or user scenario.
2. Generate multiple candidate solutions (avoiding a single assumed solution).
3. Create low-cost, quick sacrificial prototypes (sketches, storyboards, wireframes).
4. Walk stakeholders through the candidate prototypes.
5. Probe the prototypes to question the problem space (double-loop learning).
6. Extract essential requirements and throw away (sacrifice) the prototype.

**[Variant B]**

Select unclear or usability-critical requirements.
2. Rapidly build a low-fidelity mock-up or executable prototype (functional or UI).
3. Demonstrate prototype executions to stakeholders.
4. Collect user feedback and observe interaction difficulties.
5. Revise and refine requirements or prototypes.
6. Repeat until stakeholder agreement is achieved.

**[Variant C]**

Select unclear or high-risk requirements (e.g., complex UI dialogues or operational workflows).
2. Rapidly build a reduced functional or UI prototype/mock-up.
3. Demonstrate prototype execution to stakeholders in interactive sessions.
4. Collect feedback on usability, missing features, and misinterpretations.
5. Update requirements and refine or discard the prototype.
6. Repeat until stakeholder consensus is reached.

**[Variant D]**

Agree prototype objectives, scope, fidelity, and type (Throwaway or Evolutionary).
2. Construct prototype model (Horizontal scope or Vertical depth).
3. Demonstrate prototype to users in structured sessions.
4. Gather user feedback and observe interaction difficulties.
5. Refine prototype iteratively or update requirements catalogue.

**[Variant E]**

Determine prototyping approach (Throw-away vs. Evolutionary) and fidelity level (low/paper vs. high/functional).
2. Select prototyping method (Storyboarding, Paper Prototyping, Workflow Modelling, Interactive Simulation).
3. Draft initial interface screens or workflow mock-ups.
4. Present prototype to end users and elicit feedback on navigation, layout, and functionality.
5. Refine prototype iteratively based on user interactions and usability feedback.
6. Document confirmed user interface requirements or convert evolutionary model into development code.

**[Variant F]**

Select throwaway prototyping medium (paper sketches, felt boards, presentation slides, or screens-only software).
2. Build quick, deliberately rough mockups corresponding to specific scenario steps.
3. Demonstrate the prototype to stakeholders by walking through a realistic story script.
4. Allow stakeholders to 'use' the prototype (e.g. pointing at paper buttons while a 'Human CPU' switches paper screens).
5. Observe reactions and capture immediate feedback on missing data or awkward flows.
6. Throw away or refine the prototype and update the requirement specifications.

## Analyst Questions & Prompts

**[Variant A]**

"Tell me why this candidate would solve your problem?", "How would this affect the rest of your business?", "Is this addressing all of the problem or just a symptom?", "What would you do if you had this solution?", "Does this candidate suggest another better idea?"

**[Variant B]**

Does this interface layout fit your expectations? What happens when you click here? Is this workflow sequence intuitive?

**[Variant C]**

Does this screen lay out the required information logically? Is this dialogue sequence convenient for your daily work? What missing options do you need on this interface?

**[Variant D]**

Does this screen layout meet your needs? Is this navigation intuitive? What information is missing from this view?

**[Variant E]**

"How does this screen layout feel for completing task X?", "What information is missing on this dashboard view?", "Does this navigation path match your expectations?"

**[Variant F]**

Is this what you imagined? What information is missing from this screen? What button would you press next to achieve your goal?

## Minimal Realistic Example

**[Variant A]**

Sketching 5 alternative ways for college students to acquire textbooks (store purchase, second-hand search, print-on-demand, tablet download, Espresso printer) to explore their actual needs.

**[Variant B]**

Building an interactive Web screen allowing meeting initiators to select date ranges and drag-and-drop invited participants to evaluate usability.

**[Variant C]**

Creating an interactive web form mock-up for meeting initiators to select participant constraints and visualizing how schedule results are displayed.

**[Variant D]**

Developing a vertical evolutionary prototype of an online flight booking screen, refining button placement and field validation based on live user feedback.

**[Variant E]**

A BA drafts a 3-page interactive wireframe in Figma for a mobile claims app; user testing reveals that the 'Upload Photo' button needs to be on the primary screen.

**[Variant F]**

A BA draws a rough paper mockup of an electronic university enrollment screen on flipchart paper. Demonstrating it with an admissions clerk reveals that 'Prerequisite Course Verification' was missing from the initial requirements list.

## Quality Criteria & Verification

**[Variant A]**

Safe-to-fail execution; stakeholder engagement and discovery of previously hidden requirements; double-loop learning achieved (confirming or correcting the real problem).

**[Variant B]**

Stakeholder agreement on usability and workflow; alignment between updated requirements documentation and prototype behavior.

**[Variant C]**

User acceptance testing on prototype dialogues, usability fit criteria evaluation.

**[Variant D]**

User expectations managed regarding prototype performance and final system delivery; complete capture of user feedback into requirement updates.

**[Variant E]**

Elicits active user feedback; clarifies ambiguous interface requirements; keeps users focused on 'what' rather than nitpicking minor styling in low-fidelity stages.

**[Variant F]**

Immediate user feedback capture, validation of task completion speed/accuracy, throwaway lifecycle sign-off.

## Errors & Anti-Patterns

**[Variant A]**

Pygmalion effect (falling in love with a prototype); building high-fidelity or non-sacrificial prototypes too early; treating the prototype as the final specification prematurely.

**[Variant B]**

Setting unrealistically high stakeholder expectations regarding non-functional qualities (performance, security); converting 'quick and dirty' throwaway code into production systems; code-requirements mismatch.

**[Variant C]**

Misleading stakeholders regarding backend readiness; using 'quick and dirty' throwaway prototype code in production; spending excessive time building evolutionary prototypes at the expense of early requirement discovery.

**[Variant D]**

Allowing throwaway prototypes to turn into unmaintainable production code; creating over-promising prototypes with unrealistic response times; failing to document requirements learned.

**[Variant E]**

Setting unrealistic expectations where users mistake high-fidelity prototypes for finished, fully coded applications; spending excessive time polishing throw-away mockups.

**[Variant F]**

Over-polishing prototypes so users think development is finished; spending excessive time coding backend logic for a throwaway mockup; falling into UI font/color debates instead of discovering functional needs.

## When NOT to Use

**[Variant A]**

Well-understood, highly standardized technical domains with zero UI/workflow uncertainty.

**[Variant B]**

For highly stable, well-understood requirements or purely backend/non-visual computational algorithms where visual feedback adds no value.

**[Variant C]**

When requirements are purely backend, algorithmic, or heavily constrained by invisible non-functional requirements (e.g., hard real-time guarantees, batch processing).

**[Variant D]**

When requirements are already 100% stable, standardized, and non-visual (e.g. standard file format conversion).

**[Variant E]**

When solution logic is purely back-end batch processing with zero user interface or user interaction.

**[Variant F]**

When specifying backend batch algorithms, infrastructure protocols, or non-visual systems with no user interaction.
