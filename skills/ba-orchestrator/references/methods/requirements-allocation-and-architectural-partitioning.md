# Requirements Allocation and Architectural Partitioning

`T4 Modelling and Analysis › 4.5 Decomposition and Systems Analysis`

**Also described as:** System Requirements Allocation & Architectural Partitioning

## Problem Solved

Reduces structural conflicts, integration failures, and cost overruns in complex embedded/real-time systems by systematically decomposing system-level requirements and allocating them across hardware, software, and human roles.

## BA Lifecycle Phase

analysis / specification

## Input Artifacts

System Requirements Specification (SyRS), business rules, environmental constraints.

## Output Artifacts

Software Requirements Specification (SRS), Hardware Requirements Specification, Manual Requirements, Architecture Diagrams, Requirements Traceability Matrix.

## Participants & Roles

System Analyst / Requirements Engineer / System Architect (lead), System Engineer, Software Developer, Hardware Engineer, Subject Matter Expert.

## Prerequisites

Completed or draft System Requirements Specification (SyRS) describing overall system inputs, outputs, performance, safety, and quality attributes.

## Step-by-Step Procedure

Analyze system requirements and overall system architecture.
2. Partition the system into logical subsystems and components (hardware, software, manual operations).
3. Decompose high-level system requirements into derived software, hardware, and manual requirements.
4. Allocate individual derived requirements to specific architectural components based on cost, risk, and technical feasibility.
5. Define external and internal interface requirements between components.
6. Establish trace links between system requirements, derived software/hardware requirements, and allocated components.
7. Iteratively refine partitioning and allocations based on performance, cost, and risk trade-off analysis.

## Analyst Questions & Prompts

Which subsystem is best suited to perform this function? What are the physical, electrical, and timing constraints? What internal interfaces are generated by decomposing this requirement? What are the cost and risk trade-offs between implementing this in software versus hardware?

## Minimal Realistic Example

Allocating treadmill incline requirements: allocating physical motor movements to hardware, incline control logic and angle-limit calculations to embedded software, and safety stop actions to a physical tethered key.

## Quality Criteria & Verification

100% of system requirements are allocated to at least one component; all internal component interfaces are fully specified; peer reviews and architecture analysis confirm feasibility within physical and processor constraints.

## Errors & Anti-Patterns

Skimping on hardware design under the false assumption that malleable software can easily fix hardware deficiencies; improper allocation leading to overloaded processors or unachievable human performance requirements.

## When NOT to Use

Pure software applications running on standard operating systems where physical hardware architecture is not part of the project scope.

## Alternatives & Complementary Methods

Context Diagrams, State-Transition Diagrams (STD), Architecture Description Languages, Requirements Mapping Matrices.

## Supported Decisions

Architecture design decisions, hardware vs. software build trade-offs, component allocation decisions, release scoping.
