# User Story Mapping

`T5 Requirements Specification › 5.1 User Stories and Story Mapping`

This card merges 3 descriptions of the method, labelled Variant A–C in every field.

## Problem Solved

**[Variant A]**

Replaces flat, disorganized product backlogs with a structured, visual map that conveys product scope, user flow, and incremental release priorities.

**[Variant B]**

Prevents a backlog from becoming an unordered feature list; retains the end-to-end user journey and fosters shared understanding.

**[Variant C]**

Prevents losing the big picture in flat backlogs, reduces misunderstandings ('bad requirements'), eliminates Frankenstein products composed of mismatched features, and aligns cross-functional team members around shared understanding.

## BA Lifecycle Phase

**[Variant A]**

Prioritisation

**[Variant B]**

Discovery / Elicitation / Prioritisation

**[Variant C]**

Discovery / elicitation / analysis / specification / prioritisation / change management

## Input Artifacts

**[Variant A]**

Business Events, User Personas, Functional Stories, Detailed Tasks, Non-Functional Requirements.

**[Variant B]**

Stakeholder requests, user journeys, initial backlog ideas.

**[Variant C]**

Opportunity definitions, business goals, target customer/persona descriptions, stakeholder requests, existing user pain points, workflow steps.

## Output Artifacts

**[Variant A]**

Visual Story Map (Backlog), Release Slices (MVP, Release 1, Release 2), Prioritized Task Lists.

**[Variant B]**

User story map, release slices.

**[Variant C]**

User Story Map (grid/backbone structure of activities, steps, and user tasks), sliced release strategy/roadmap, MVP scope specification, story-mapped backlog.

## Participants & Roles

**[Variant A]**

Product Owner, Business Analyst, Agile Development Team, UX Designer, Key Stakeholders.

**[Variant B]**

Product Manager, Business Analyst, Stakeholders, Developers, Testers.

**[Variant C]**

Product Owner / Manager, Business Analyst, User Experience Designer, Software Developers, Testers, Business Stakeholders, Subject Matter Experts (SMEs), End Users / Customers.

## Prerequisites

**[Variant A]**

Identified customer personas, work scope, and high-level business events.

**[Variant B]**

High-level understanding of user goals and main workflow steps.

**[Variant C]**

Defined business opportunity/problem statement, target market/user identification, access to key stakeholders or team collaborators, sticky notes/cards and writing instruments or digital mapping tool.

## Step-by-Step Procedure

**[Variant A]**

Lay out the top row of the map: Business Event Stories across the horizontal axis (representing the end-to-end user flow).
2. Under each Business Event Story, add Functional Stories representing key functional steps.
3. Under each Functional Story, add columns of Detailed Tasks in descending order of priority/sophistication.
4. Annotate cards with user profiles, wireframes, and Non-Functional Requirements.
5. Draw horizontal slice lines across the map to define releases (MVP, Release 1, etc.).
6. Pull stories iteratively from the map for sprint development.

**[Variant B]**

Frame the problem and user goals.
2. Map the big-picture user journey (activities and tasks) horizontally.
3. Slice features/stories vertically under each task by priority.
4. Define release boundaries.

**[Variant C]**

Frame the problem and identify business goals.
2. Identify target personas/users and their needs.
3. Map the big picture (backbone) left-to-right in narrative flow (activities and high-level steps).
4. Explore details, alternatives, and variations vertically under each step.
5. Slice the map horizontally into releases (MVPs/MVPes) prioritized by target outcomes.
6. Slice out a development strategy (walking skeleton, opening/mid/endgame) to manage technical risk and budget.

## Analyst Questions & Prompts

**[Variant A]**

"What is the end-to-end flow of events a user experiences?", "What functional steps make up this event response?", "Which tasks are absolute 'Must Haves' for a minimal viable release?", "What non-functional requirements apply to this task?"

**[Variant B]**

What is the user trying to achieve from start to finish? What is the next logical step in the journey? What is the minimum viable slice for this release?

**[Variant C]**

"Who is this for?", "What problem does this solve?", "First they do this, and then what?", "What are the specific things they do here?", "What alternative things could they do?", "What about when things go wrong?", "What is the absolute minimum needed to reach this specific outcome?"

## Minimal Realistic Example

**[Variant A]**

Mapping a flight booking system with top-level events ('Find flights', 'Model & compare', 'Make reservation', 'Pay'), with vertical columns of detailed tasks sliced horizontally into MVP and Release 1.

**[Variant B]**

A case analyst reviews a case submission starting from intake, evaluating evidence, viewing system recommendation, to final decision.

**[Variant C]**

Mapping a morning routine: Activities across the top backbone ('Waking Up', 'Getting Cleaned Up', 'Getting Dressed', 'Eating Breakfast'); steps underneath ('Hit snooze', 'Take a shower', 'Brush teeth', 'Put on clothes', 'Make coffee'); slicing horizontally by outcome ('Get out the door in 5 minutes' vs. 'Luxurious morning').

## Quality Criteria & Verification

**[Variant A]**

Map provides a complete, understandable horizontal narrative of the product; vertical columns are strictly prioritized; releases represent viable, deliverable slices of business value.

**[Variant B]**

Story map clearly shows complete end-to-end user journey and actionable, prioritized release slices.

**[Variant C]**

Shared understanding among the whole cross-functional team; clear narrative flow from left to right; visible slice lines matching business outcomes; peer review/walkthrough with stakeholders; prototype testing with end users.

## Errors & Anti-Patterns

**[Variant A]**

Building a story map without top-level business event backbone (creating a flat, unorganized list); neglecting non-functional requirements on the map.

**[Variant B]**

Treating user stories as self-sufficient specifications or replacing detailed requirements, rules, and quality criteria entirely.

**[Variant C]**

Flat backlog trap; treating the map as a substitute for conversations; template zombie syndrome (forcing every stickynote into rigid user story formats); trying to map every single system feature instead of focus area; client-vendor order-taking anti-pattern.

## When NOT to Use

**[Variant A]**

Single, isolated bug-fix tasks or small standalone script developments.

**[Variant B]**

When detailed functional behavior, multi-step system interactions, or complex decision logic must be precisely specified.

**[Variant C]**

Trivial single-fix changes; low-risk routine bugs; environments where stakeholders and developers have no access or willingness to collaborate or hold conversations; when outcomes are fixed and non-negotiable without any ambiguity.

## Alternatives & Complementary Methods

**[Variant A]**

Flat Product Backlog, Impact Mapping, Feature Breakdown Structure, Event Storming.

**[Variant B]**

Use Cases (for detailed interaction), Atomic Requirements, Decision Tables.

**[Variant C]**

Flat Product Backlog, Impact Mapping, Customer Journey Mapping, Design Studio, Personas, Prototyping/Wireframing, Acceptance Criteria Specification (3 Cs).

## Supported Decisions

**[Variant A]**

Release planning, MVP definition, sprint backlog selection, incremental delivery scheduling.

**[Variant B]**

Scope, priority, release planning.

**[Variant C]**

Scope determination, release roadmap slicing, MVP definition, feature prioritization based on outcome, technical risk mitigation sequence, sprint planning.

## AI & Agentic Adaptation

**[Variant A]**

Agile management tools with AI can automatically structure flat story lists into visual story maps based on event dependencies, suggesting optimal release slices based on velocity estimates.

**[Variant B]**

Can be used to map multi-agent or human-in-the-loop workflows across distinct interaction steps.

**[Variant C]**

Not in source
