# Requirements Engineering Process (End-to-End)

`T5 Requirements Specification › 5.6 Requirements Documents and Phrasing`

**Also described as:** Requirements Engineering (Elicitation, Analysis, Specification, Validation)

## Problem Solved

Reduces ambiguity, miscommunication, scope creep, conflicting requirements, and solution delivery failure.

## BA Lifecycle Phase

Elicitation / Analysis / Specification / Prioritisation / Validation

## Input Artifacts

Project charter/ToR, business case, 'to be' process models, stakeholder interviews, user roles/personas.

## Output Artifacts

Requirements catalogue, User stories/product backlog, Use case diagrams/descriptions, Data models (ERD/Class model), BRD.

## Participants & Roles

Sponsor, Product Owner, BA, SME, Developer, Tester, Solution Architect.

## Prerequisites

Agreed project scope, identified stakeholders, defined business objectives.

## Step-by-Step Procedure

Elicit requirements using qualitative and quantitative techniques.
2. Uncover tacit knowledge and resolve assumptions.
3. Analyse and filter requirements (check for clarity, completeness, feasibility, correctness).
4. Structure and model requirements (use cases, data models, process models).
5. Document requirements (catalogue or user stories with acceptance criteria).
6. Prioritise requirements (MoSCoW/INVEST).
7. Validate requirements with stakeholders for baseline or backlog readiness.
8. Manage changes and maintain traceability.

## Analyst Questions & Prompts

As a role, why do you want feature? What is the acceptance criterion? Is this requirement atomic, testable, and unambiguous? What happens in exception scenarios?

## Minimal Realistic Example

Defining, modelling, and validating functional and non-functional requirements for an online retail portal, categorising them using MoSCoW, and creating an ERD to capture data rules.

## Quality Criteria & Verification

Requirements meet quality criteria (Clear, Concise, Consistent, Relevant, Unambiguous, Correct, Testable, Traceable), validated via formal walkthroughs or INVEST checks.

## Errors & Anti-Patterns

Treating elicitation as passive 'requirement gathering', confusing solutions with requirements, ignoring non-functional requirements, neglecting tacit knowledge.

## When NOT to Use

When using a pure COTS package with zero customization allowed, though user needs still drive selection.

## Alternatives & Complementary Methods

User Stories, Use Case Modelling, Prototyping, Class Modelling, ERD, MoSCoW, INVEST.

## Supported Decisions

Scope, release planning, acceptance criteria, architecture, compliance.

## AI & Agentic Adaptation

AI agents can evaluate requirements sets for ambiguity, testability, and conflict, generate draft user stories, and automatically maintain traceability matrices.
