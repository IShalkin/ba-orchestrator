# Feature Requirements

`T5 Requirements Specification › 5.6 Requirements Documents and Phrasing`

## Problem Solved

Communicates required product functionality clearly in traditional textual format for simple extensions or technical component purchases.

## BA Lifecycle Phase

specification

## Input Artifacts

Stakeholder wishlists, event lists, domain problems.

## Output Artifacts

Numbered textual feature requirement statements ('The product shall...').

## Participants & Roles

BA, developer, customer.

## Prerequisites

Clear domain understanding by the analyst.

## Step-by-Step Procedure

Identify required product capabilities from task studies or domain problems.
2. Draft textual feature statements specifying product capability.
3. Add domain context and 'why' background rationale to resolve potential ambiguities.
4. Review feature statements with developers and SMEs for clarity and feasibility.

## Analyst Questions & Prompts

Why do you need this feature? What specific problem does this functionality solve in your task?

## Minimal Realistic Example

R1: The product shall be able to record that a room is occupied for repair in a specified period.

## Quality Criteria & Verification

Verification testing (pass/fail per feature), developer code review.

## Errors & Anti-Patterns

Creating endless feature 'wishlists' disconnected from real business tasks, leading to bloated, unusable systems.

## When NOT to Use

COTS business application tenders where feature lists lock out superior standard software workflows.

## Alternatives & Complementary Methods

Task Descriptions, Tasks & Support, Use Cases.

## Supported Decisions

Software build specifications, acceptance test verification lists.

## AI & Agentic Adaptation

Refactor raw user feature requests into precise 'shall' statements enriched with domain rationale prompts.
